### U01. ACCEPTANCE says only the first run of rows 3 and 12 asks tx.fhir.org, but every run does, and an offline rerun makes the README's 'terminology on' claim fail (partly fixed)
- Severity: cosmetic
- Where: docs/ACCEPTANCE.md:19; scripts/fhir_validate.py:150-155 and :187-196; README.md:19-20 (claim terminology_checks_ran = True) and the badge at README.md:15 ('0 errors, terminology on')
- Compared: Round 11 asked each network row to say what it needs, and the gitleaks and row 14 parts are now done. BlackBox's ACCEPTANCE names on each row what that row needs (row 1 names its docker quickstart).
- Evidence: ACCEPTANCE.md:19 reads 'Three rows in the first table need a network: the first run of rows 3 and 12 fetches their guide, SUSHI and the HL7 validator, and asks tx.fhir.org for terminology'. But fhir_validate.py calls tx_reachable(DEFAULT_TX) on every run, not only the first. When tx.fhir.org does not answer, it prints 'terminology checks are off this run', sets tx to n/a, and writes 'terminology_checks_ran': false into results/fhir_validation.json with no error. The README's claim comment wants True. In my clone, setting that field to false made verify_claims print 'claim value drifted: results/fhir_validation.json#/terminology_checks_ran README says True, results say False'. So a judge who reruns row 3 or 12 offline, as the sentence suggests they can, gets row 4 red, and row 12 red on the next make check, since verify-claims runs before fhir-validate. The path is narrow: it needs an offline rerun.
- Fix: Write 'Rows 3 and 12 need a network on every run: the first run fetches their guide, SUSHI and the HL7 validator, and every run asks tx.fhir.org for terminology. Offline, the validator runs with terminology off and records that, and make verify-claims then refuses it.' Or have fhir_validate.py leave results/fhir_validation.json as it is when the terminology server does not answer, and say so.
