## Which hosting path won, and why

**Web: a static export on Cloudflare Pages.** It won on the first try, inside its 60 minute box,
so the OpenNext adapter was never needed. Four things had to change: two dynamic routes became
query routes (`/spot?id=` and `/quick?spot=`), the share card and the web app manifest are written
at build time, `/demo` reads its query in the browser, and the security headers moved into
`public/_headers`. That last one is the one that mattered. A static export gets no headers from
Next at all, so the strict policy would have vanished on deploy without anyone noticing. There is
now one definition in `apps/web/security-headers.mjs` that both the server build and the
`_headers` file come from, and the policy is verified on the live site.

**API: a TypeScript Worker on D1.** The Python Worker was the brief's first choice and it was
probed properly before being dropped. FastAPI genuinely is supported on Python Workers, and
Cloudflare's own docs say synchronous SQLAlchemy ORMs work. But a D1 binding is
`env.DB.prepare(sql).bind(...).run()`. It is not a DBAPI connection and there is no D1 dialect
for SQLAlchemy, while `apps/api/study.py` is SQLModel from top to bottom. Reaching D1 from that
code means writing a DBAPI shim, which is not a 90 minute job and would sit under the one part of
the system that must not be wrong. Separately, `pywrangler` needs uv 0.12.3 and this machine has
0.11.28, and upgrading uv nine days out on a repo that runs everything through `uv run` is a bad
trade for a path already blocked. So the brief's stated fallback was taken.

Nothing needs a card. No new account. `npx wrangler whoami` was already logged in, so there is no
command waiting for Alex.

## The new consensus method on synthetic data

The old rule weighted a vote by the other three items of the same feature. It was biased on a set
this small. The replacement splits the 16 items into two halves with two of each feature, passes a
person on one half with 6 of 8, and votes on the other half by plain majority, once with everyone
and once with only the passers, falling back to everyone when nobody passes or the passers tie.

At the plan's own resolution, 200 splits and 2,000 draws:

| Case | Everyone | Passers only | Gain |
|---|---|---|---|
| A third of people answer at random | 0.8862 | 0.8928 | **+0.0066** |
| Equal skill | 0.8195 | 0.7750 | **-0.0445** |
| Nobody passes | identical, every item falls back | identical | 0.0000 |

So the honest finding is that the filter helps a little when a fair share of people tap at random,
and actively hurts when everyone is about as good as everyone else, because it throws away good
votes. That is why it is exploratory, why it is off the README's first screen, and why the
consensus beat is out of the video script. Ten tests cover it, including the three cases the brief
names, and the property tests that covered the old weighted arithmetic were rewritten for this.
